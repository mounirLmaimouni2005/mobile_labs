# PHP Examples and Tutorials

## Role

Make short, clear PHP examples that run by themselves or fit the user's real project.

## When to use this Skill

Use it for PHP exercises, language examples, Laravel examples, or learning materials. Do not use it to rewrite a full app without a clear request.

## Read first

- Read the full README, useful rules, and files near the files you will change.
- Check `composer.json`, project rules, and code when they exist. Check the PHP version you can run. Do not call it the project's minimum version unless the files say so.
- Look for classes and services that already exist. Do not make up classes, packages, versions, or real problems.
- If a small example can answer the request, use it and say what is only an example. Ask a question only when the choice changes the result.

## Steps

1. Check what file the user needs. Read current files before you change them.
2. Check the PHP version, packages, framework, file loader, and style from real project files. Do not make up missing facts.
3. Use the file paths in the README. For this PHP Lab, make one PHP example and one tutorial for each topic. Keep the same number in both file names.
4. Write for new learners. Each tutorial needs the meaning, use, main code, example, good ways to work, common mistakes, run command, result, and an exercise.
5. Keep the tutorial and example in line. Use the same names, input, commands, actions, and result. Each example must run alone and need no missing package. Say when an example is only for learning.
6. Keep code short and clear. Use clear names and values. Handle exceptions at a good place. Use namespaces only with the real file loader, or say that the example runs alone. Use a trait only for a real shared action.
7. Do not make up an app, design, package, PHP version, or real problem. Say when an idea is only a way to use the topic.
8. Run `php -l` on each PHP file and run each example when PHP is ready. Check that the real result matches the tutorial and slides. Run current project tests when they exist. Write checks that could not run as not done.
9. Change the main README only when the user asks for it. Do not change slides when the request is only about examples.
10. Give a short report of changed files, commands, results, and limits.

## Rules

- Reply in the user's language. Keep the language and style of current files.
- Use a stand-alone example when it is easier to understand. If it needs a framework, follow real rules. Do not fake framework code.
- Do not show secrets or change `.env`.
- Do not add packages for simple PHP examples.
- Do not show made-up data as real data. Do not say an example is part of an app when it is not.
- Change only the files needed for the request.

## Example requests

- "Make a PHP exception example for this form."
- "Make three exercises about namespaces, traits, and exceptions."
- "Change this example to use the PHP version and Composer setup in my project."

## Final check

- Each topic has one tutorial and one PHP example with the file names in the README.
- Each tutorial is clear for new learners and has the main code, good ways to work, common mistakes, a run command, a result, and an exercise.
- Each example runs alone and shows the result in its tutorial.
- Use the PHP version and project rules that were checked. Do not say they are project needs unless the project says so.
- Report checks and limits honestly.
